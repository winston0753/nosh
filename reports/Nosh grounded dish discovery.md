# Nosh can ground discovery without a catalog

November 1, 2026 · Research and strategy proposal, not an accepted implementation change

**Yes: removing automatic delivery makes this a substantially lighter, viable direction to test. Nosh can recommend a dish, find a nearby restaurant and show its location without maintaining a comprehensive restaurant database.** Catalog-free discovery does not have to mean guessing: Nosh can consult live sources when needed. The distinction is between asking a language model what it remembers and giving it tools that retrieve evidence about actual restaurants and menus. ChatGPT or Claude can help interpret food preferences and inspect sources; neither automatically knows the user's precise location or guarantees a current dish-to-restaurant match. My recommendation is a small, evidence-led dish-discovery product using live place lookup and merchant-menu evidence, with a limited food vocabulary and a feedback loop around meals people actually enjoyed. A worldwide ontology is unnecessary to establish whether that experience is valuable.

The comparison with existing Nosh matters. D021, D022 and D027 already replace the curated restaurant catalog with live Google Places, retaining provider identifiers and Nosh-owned data. The proposed change therefore does not newly remove the need for an owned restaurant directory. It changes the starting point from “try this restaurant” to “try this dish,” and adds the question of which nearby establishment actually serves it. Removing delivery eliminates a large operational layer; resolving that last question remains the central data problem. ([Nosh decisions](/Users/winstontang/Downloads/nosh/DECISIONS.md))

**There are three increasingly grounded ways to build the experience.** The simplest is model recall: tell the model a dish and neighborhood and request a restaurant. This is useful for brainstorming candidates, but inadequate as the evidence behind a meal recommendation. A plausible name, address or cuisine association does not establish the correct branch or current menu. The second approach enables live web search and asks the model to inspect sources. This can support an early prototype without an owned catalog, but quality varies with what is indexed, accessible and current. The third combines web or model assistance with structured place lookup and branch-specific menu evidence. It requires more integration, but makes restaurant identity, proximity and the basis for the dish claim easier to check.

Both major model providers support the second approach. OpenAI's web-search API accepts an approximate location expressed through country, city, region and timezone; responses provide source annotations, and displayed web-derived information requires visible, clickable citations. Claude's search tool accepts comparable location fields and provides citations and domain controls; its separate fetch tool can read a discovered menu page. These are documented API capabilities, not a promise that wrapping a consumer chat interface reproduces that product's entire context and tool setup. ([OpenAI web search](https://developers.openai.com/api/docs/guides/tools-web-search), [Claude web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [Claude web fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool))

**The phone supplies location; the model does not magically acquire it.** Nosh should request foreground location when opened, or accept a neighborhood or saved fallback spot. A city-level search hint is useful for relevance but insufficient to enforce a short walk. Keep precise coordinates out of general prompts and application logs; send them transiently only where location matching requires them. That is a proposed privacy design, not an assertion that API providers automatically remove location information. There is no need to introduce background tracking for this experience.

Google Places Text Search supplies food-oriented candidate lookup, location bias or restriction, opening filters and stable place identities. Its responses are places, however, rather than verified menu inventory. A location bias can return results outside the preferred area; it should not be presented as a strict radius. Maps URLs can then open a particular establishment, using a place ID to reduce ambiguity. The especially lightweight alternative is to open a Maps search for the accepted dish and area, but that leaves restaurant selection to Maps rather than delivering Nosh's stronger promise of choosing one place. ([Places Text Search](https://developers.google.com/maps/documentation/places/web-service/text-search), [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started))

The proposed product should distinguish **“restaurant found,” “dish listed,” and “available now.”** A place record supports the first claim. A menu for the correct branch supports the second. The third needs current merchant evidence that ordinary search often cannot provide. A page checked today can still contain last year's menu; inspection time is not publication time. A chain-wide menu, old review, seasonal special or similarly named preparation can also produce a convincing false match. Use clear evidence descriptions such as “listed on this branch's online menu,” with an accessible source, rather than an arbitrary “92% confidence” supplied by the model. Unknown stock, price or menu freshness should remain unknown.

I would also change the internal sequence slightly: **check plausible local supply before making a dish enticing.** The user can still see a dish first and accept before seeing the restaurant. Behind that interaction, Nosh should already have some evidence of a nearby serving, then refresh relevant details after acceptance. Otherwise the app repeatedly sells an appealing idea and discovers afterward that the user cannot reasonably eat it. With Nosh's foreground-location rule, this check belongs after opening the app unless a valid declared location is available. A general mealtime nudge remains simpler than a notification promising a locally available dish. ([Current notification and location decisions](/Users/winstontang/Downloads/nosh/DECISIONS.md))

DoorDash's published engineering makes this distinction particularly clear. Its June 2026 Assistant overview describes memory plus tools that search real restaurants and catalog items. It explicitly identifies changing menus, hours, locations and inventory as information that must come from live systems, and discusses failures such as closed stores, wrong prices and nonexistent cart changes. **DoorDash's language-model layer does not replace its operational data; it interprets requests and acts through that data.** Nosh can adopt that separation without copying the commerce infrastructure. ([DoorDash Assistant engineering](https://careersatdoordash.com/blog/building-doordash-assistant-an-engineering-overview/))

The older recommendation architecture gives useful context, although it should not be mistaken for a complete description of today's system. DoorDash's October 2022 homepage account describes staged retrieval and ranking using cuisine, price, user history, time and practical context, followed by exploration to avoid concentrating only on familiar choices. Its November 2024 search account links queries to dish, cuisine, meal and dietary concepts through taxonomy and knowledge-graph metadata; an LLM helps identify concepts that retrieve actual indexed items or stores. The ontology supplies meaning, while the catalog supplies candidates. ([2022 homepage architecture](https://careersatdoordash.com/blog/homepage-recommendation-with-exploitation-and-exploration/), [2024 search retrieval](https://careersatdoordash.com/blog/how-doordash-leverages-llms-for-better-search-retrieval/))

Newer articles extend this approach. DoorDash described consumer, merchant and item profiles in July 2025, drawing from menus, transactions, descriptions and other evidence. Its April 2026 embeddings article describes offline merchant/item representations refreshed as source content changes, then online query retrieval and ranking. A May 2026 grocery example generates personalized search intents offline and retrieves actual catalog items online. These are different surfaces and stages, not one universal pipeline or proof that every component is deployed identically. They nevertheless offer a useful small-company lesson: do expensive semantic preparation where helpful, then resolve real options at use time. ([Profiles](https://careersatdoordash.com/blog/doordash-profile-generation-llms-understanding-consumers-merchants-and-items/), [Content embeddings](https://careersatdoordash.com/blog/doordash-llms-to-build-content-embeddings-for-search-and-recommendations/), [Offline generation and online retrieval](https://careersatdoordash.com/blog/doordash-offline-llms-online-personalization-generating-carousels/))

DoorDash is also a broader competitor than delivery alone. Its June 2026 Ask DoorDash announcement describes conversational restaurant discovery, budget and dietary refinement, and suggested carts informed partly by previous orders, initially in selected US areas on iOS. It announced reservations in San Francisco, Los Angeles and Boston in May 2026, and separately supports pickup. Those announcements establish relevant capabilities; they do not verify every user's access in November. Nosh cannot rely on “conversational food discovery” or “dine-in instead of delivery” as an uncontested gap. ([Ask DoorDash](https://about.doordash.com/en-us/news/ask-doordash), [Reservations expansion](https://about.doordash.com/en-us/news/los-angeles-san-francisco-boston-reservations), [Pickup documentation](https://help.doordash.com/en-ca/merchants/article/what-is-doordash-pickup))

Its limitations need equally precise treatment. DoorDash's assistant help acknowledges potentially outdated product information and AI mistakes. Sponsored Listings are documented on homepage and search surfaces, but that does not establish paid influence inside every conversational answer. It is reasonable to infer that catalog-grounded discovery cannot guarantee every neighborhood dish; it is not justified to claim that DoorDash only recommends delivery partners or lacks cross-cuisine exploration. Nosh's potential broader coverage, better enjoyment and lower decision effort remain hypotheses requiring comparison. ([Assistant help](https://help.doordash.com/en-ca/consumers/article/meet-your-new-ai-grocery-assistant), [Sponsored Listings](https://merchants.doordash.com/en-us/learning-center/sponsored-listings))

Nosh's own knowledge should concentrate on what helps it improve over repeated meals: dish identities and aliases, useful variants and traits, explicit interests, and confirmed experiences. Keep these separate from externally sourced venue facts. Google's policies permit indefinite place-ID retention while restricting other caching; its terms also restrict creating content from Maps content and specified AI uses. Passing a provider response through a model does not make derived labels or embeddings freely owned. Independent merchant sources also need appropriate rights before durable ingestion. ([Places policies](https://developers.google.com/maps/documentation/places/web-service/policies), [Maps terms](https://cloud.google.com/maps-platform/terms))

**A useful taste graph can begin small.** A dish concept, a restaurant's particular version and a person's experience are different records. Shared texture or preparation can explain an invitation to explore, but cannot establish that someone will like the result. A yes tap records present interest; later confirmation establishes whether they tried it and would eat it again. A poor serving should not automatically condemn a cuisine. A new dish at a familiar restaurant can be a successful discovery, which would change Nosh's current emphasis on previously unvisited restaurants. Its existing separation between acceptance and confirmed enjoyment is therefore worth preserving. ([Nosh recommendation semantics](/Users/winstontang/Downloads/nosh/RECOMMENDATIONS.md))

A thin model wrapper would answer essentially the same question as a general assistant with a new interface. A stronger Nosh would remember what the person actually explored, select a manageable next step, reliably connect it to a nearby serving, and learn from the meal. That is a defensibility hypothesis, not a moat already created by storing a graph. The promise should remain understandable: help someone discover another dish they genuinely enjoy with little effort.

I recommend beginning with **roughly 30 dish-and-location cases in one neighborhood**, an illustrative feasibility sample rather than a statistically powered study. Compare direct Places lookup against web-enabled model lookup and the combined approach, using the same cases and a consistent manual review. Include uncommon aliases, chain branches, seasonal dishes, missing menus and deliberately unavailable requests. Evaluate correct identity, correct branch, explicit menu match, proximity, honest abstention, source freshness, waiting time, paid calls and manual checking time. A system that declines an unsupported match can be better than one that always returns an attractive answer.

Then test the user experience with a small consenting cohort and a modest dish vocabulary. Measure confirmed trial, enjoyment, voluntary repeat use, failed outings and decision effort; compare simple dish suggestions with graph-informed exploration before expanding the ontology. Set acceptable error and labor thresholds beforehand. No reviewed source establishes Nosh's likely cost per recommendation, latency, retention or improvement over ordinary Maps, so those values should come from the pilot rather than a forecast disguised as evidence.

This research authorizes no implementation change. Runtime model search would require a deliberate revision to Nosh's deterministic, no-LLM mealtime rule, alongside decisions about evidence standards, dish identity and the success metric. Existing authentication, schedules, sessions and reliable feedback writes remain useful. The next investment should establish whether a small, grounded food guide earns repeat use. If it does, expand the knowledge according to the dishes users request and the discoveries they enjoy; that gives the ontology a sustainable purpose without making completeness a prerequisite.

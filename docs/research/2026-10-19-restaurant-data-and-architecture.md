# Build Nosh’s catalog around durable data

**Use Overture to seed a small, reviewed restaurant catalog, keep ratings optional, and learn quality from Nosh’s confirmed visits. Do not use standard Google Places API access to populate a permanent ratings database.** Overture fits durable storage and offline cards; Google’s richer information comes with materially different storage and display restrictions. Direct Foursquare open data is worth benchmarking only for incremental neighborhood coverage. The existing Expo, FastAPI, PostGIS and deterministic recommendation architecture is appropriate. The immediate work is a real catalog with correction and refresh rules, followed by completing Milestone 3—not a stack rewrite or notification rollout.

This assessment combines provider documentation researched October 16, 2026, with an October 19 recheck of Overture’s core schema and Google’s service terms and pricing, plus a refreshed repository review. Provider rights interpretations assume **standard US/non-EEA terms**, not a negotiated agreement. No neighborhood extract, paid API request, or accuracy benchmark was performed; source superiority remains unmeasured.

## Overture supplies restaurant facts, not dining ratings

Overture Places includes names, coordinates, addresses, taxonomy, contact details, provenance, existence confidence and operating status. Its current schema has **no consumer ratings, review counts, opening hours or prices**. Operating status distinguishes continued operation from closure; it does not establish “open now.” Existence confidence is not evidence that the food is good. Current ingestion must use `taxonomy` and `basic_category`: the former `categories` field was removed in September 2026. The current guide explicitly acknowledges duplicates and incomplete properties. These are manageable inputs to a reviewed pilot, not a ready-made trusted catalog. ([Place schema](https://docs.overturemaps.org/schema/reference/places/place/), [Places guide](https://docs.overturemaps.org/guides/places/))

A bounded DuckDB query against cloud Parquet can extract the intended neighborhoods without downloading the world. Monthly releases suit a small refresh job, but they cannot support a real-time opening guarantee. Retain the permitted input subset, release identifier and transformation version for reproducibility: Overture’s public release retention is limited to 60 days, which concerns hosted availability rather than a prohibition on retaining licensed data. ([DuckDB access](https://docs.overturemaps.org/getting-data/duckdb/), [Release calendar](https://docs.overturemaps.org/release-calendar/))

Storage rights must follow the **actual provider and release**. Current Overture documentation identifies contributions under CDLA Permissive 2.0, Foursquare under Apache 2.0 with NOTICE obligations, and AllThePlaces under CC0. The Places guide states that this theme contains no OpenStreetMap data; assuming every Overture theme carries ODbL would be incorrect. Preserve required licenses, notices and modification attribution with distributed data and appropriate app/API documentation. Official attribution and guide pages are not perfectly synchronized, so use a reviewed release manifest instead of a blanket “Overture licensed” flag. ([Attribution](https://docs.overturemaps.org/attribution/), [Places guide](https://docs.overturemaps.org/guides/places/), [CDLA](https://cdla.dev/permissive-2-0/), [Foursquare NOTICE](https://opensource.foursquare.com/places-notice-txt/))

**Direct Foursquare OS Places is the strongest alternative to test**, not a proven winner. It offers categories, contact information, refresh/closure dates and merge redirects, but its open schema also lacks consumer ratings, hours and prices. A refresh date does not mean every field was verified. Access now uses the Places Portal and an Iceberg catalog rather than the deprecated public S3 path. Because Overture already incorporates Foursquare contributions, measure unique correct restaurants added; two records sharing an upstream source are not independent confirmation. ([OS schema](https://docs.foursquare.com/data-products/docs/places-os-data-schema), [Current access](https://docs.foursquare.com/data-products/docs/access-fsq-os-places))

Foursquare’s commercial Pro/Premium datasets include ratings, hours and price, making a **negotiated dataset license** a plausible later purchase if stars demonstrably improve the product. Its veracity score measures data reliability, not dining quality. No price or agreement granting Nosh’s desired permanent storage, offline display and derived ranking rights was established here. OpenStreetMap can fill factual gaps such as cuisine/hours, but offers no consumer-star corpus and introduces ODbL attribution/share-alike considerations; separate tables alone do not remove those obligations. Yelp’s short caching allowance and restrictions on analysis also make its standard integration a poor default for this permanent database. ([Foursquare rich schema](https://docs.foursquare.com/data-products/docs/places-pro-and-premium), [Commercial delivery](https://docs.foursquare.com/data-products/docs/places-flat-file-overview), [OSM license](https://www.openstreetmap.org/copyright), [Yelp FAQ](https://docs.developer.yelp.com/docs/places-faq))

## Google works better as optional live information

Google Places provides useful ratings, hours and business details, but standard terms restrict extracting, indexing and storing Maps content, including business names, addresses and reviews. The Places exception permits latitude/longitude caching for **30 days**, not general caching of ratings or restaurant details. Place IDs can be retained. Consequently, a nightly refresh, a short expiration time, or manually copying ratings does not establish permission to warehouse them. Persisting a Google-derived quality score or recommendation snapshot is also not an established workaround. ([Platform terms](https://cloud.google.com/maps-platform/terms), [Service-specific terms](https://cloud.google.com/maps-platform/terms/maps-service-terms), [Place IDs](https://developers.google.com/maps/documentation/places/web-service/place-id))

Google permits mapless Places display but generally restricts use with non-Google maps. The published language does not conclusively settle every mapless card followed by an external Apple Maps handoff; obtain clarification for that exact custom REST flow rather than declaring it universally permitted or forbidden. **Places UI Kit has an explicit any-map exception**, including non-Google maps. That makes it a stronger candidate for a later optional details panel, while leaving storage restrictions intact. Its iOS components use SwiftUI, so integrating them into this Expo app needs a separate compatibility assessment; no tested React Native integration was established. ([Service-specific terms, §§14–15](https://cloud.google.com/maps-platform/terms/maps-service-terms), [iOS UI Kit](https://developers.google.com/maps/documentation/places/ios-sdk/places-ui-kit-overview))

If added, let Nosh select restaurants entirely from independently licensed data, then render Google information live through a reviewed ID mapping. Keep Google content out of canonical metadata, offline caches, logs, analytics payloads and ranking snapshots; preserve Google and author attribution. A failed request must leave the independent Nosh card usable. Nearby Search’s maximum 20 results per request also makes it unsuitable as an exhaustive neighborhood inventory. ([Places policies](https://developers.google.com/maps/documentation/places/web-service/policies), [Nearby Search](https://developers.google.com/maps/documentation/places/web-service/nearby-search))

Cost is secondary to these rights. Illustratively, 50 daily users viewing two cards per day for 30 days create 3,000 requests; 500 create 30,000, assuming one billable request per card. At current published tiers, Details Enterprise for ratings/hours costs approximately **$40 or $580/month**, respectively, after its 1,000-request free cap. Basic UI Kit display costs approximately **$0 or $20**, after its 10,000-request cap, but is not a ratings-extraction license. These scenarios exclude discovery, matching, retries, reloads, photos, taxes and other usage sharing the billing account. Use explicit field masks, bounded retries, enforceable quotas and billing alerts if integrating. ([Pricing](https://developers.google.com/maps/billing-and-pricing/pricing), [Details field tiers](https://developers.google.com/maps/documentation/places/web-service/place-details))

## A small reviewed pipeline is the better immediate investment

The proposed pipeline is **bounded extract → staging → deterministic taxonomy mapping → validation and human review → canonical upsert**. Select two public neighborhood areas, define eligible venue types, and pin one Overture release. Extract these areas independently of private user home/work coordinates. Preserve raw categories and map them through a versioned cuisine table; “restaurant” alone does not identify a cuisine. Unknown identity, cuisine or status should produce a review reason rather than an invisible omission.

Retain Nosh’s own place UUID and existing provider crosswalk. Match exact provider IDs first, then review conservative candidates based on location plus name/address/contact evidence. Never merge restaurants on proximity alone. GERS IDs are useful but can change after moves, splits and merges; disappearance from a release does not prove closure. Preserve aliases and visit history, treat missing records as stale/reviewable, and protect manual overrides from subsequent refreshes. For this scale, a monthly complete neighborhood refresh is simpler than a global delta system. ([GERS stability](https://docs.overturemaps.org/gers/stability/), [Changelog semantics](https://docs.overturemaps.org/gers/changelog/))

Add only the source contract needed now: provider/release/schema, source and ingestion timestamps, applicable license/NOTICE, field overrides, verification date and review status. Keep existence confidence, public rating, editorial judgment and Nosh outcomes distinct. Unknown quality can remain neutral; verifying an address should not produce a high quality score. Restaurant-owned sites or direct confirmation can resolve missing facts, with source/date recorded, without copying reviews or photos wholesale.

Before choosing between Overture and direct Foursquare, create an independent reviewed neighborhood list and measure eligible-place precision, reference-list recall, duplicate rate, coordinate/address correctness, cuisine completeness and incremental coverage. Recall against that list is not proof of whole-neighborhood completeness. Review every admitted pilot record for identity, supported cuisine, location, active status and usable Apple Maps destination. Require zero unresolved identity collisions, complete provenance/notices, repeat-import idempotency, preserved manual corrections, and tested rename/closure/replacement cases. Also measure how many unvisited eligible candidates remain in representative contexts after normal filtering. Agree on a minimum useful supply before testing; do not invent a success count from global provider totals. These are proposed acceptance gates, not results already achieved.

## Preserve the foundation and fix the remaining trust gaps

The current catalog still contains **20 fictional development fixtures**, and the loader only inserts missing records; the relocated job calls that loader rather than ingesting a provider. Source rows already support canonical UUIDs and provider identifiers, but lack an enforced release, rights, override and review contract. Real-data admission is therefore the first work package. Validate quality as finite and bounded, give it an explicit provenance, and reserve “Highly rated” for supported rating evidence: the current engine produces that label from an arbitrary metadata score above 0.7, and quality contributes 45% of the within-cuisine score. ([Fixtures](/Users/winstontang/Downloads/nosh/services/api/app/places/fixtures.py:1), [Loader](/Users/winstontang/Downloads/nosh/services/api/app/places/service.py:19), [Reason generation](/Users/winstontang/Downloads/nosh/services/api/app/recommendations/engine.py:141))

Keep the indexed PostGIS radius query, pure ranking functions and transactional suggestion/visit workflows. The October 16 hardening addressed schedule validation, onboarding provenance, cuisine priors, response replay and several concurrent-write paths; those should not be reported as outstanding defects. **HTTP response replay and recommendation reproducibility are different guarantees.** The remaining ranking issue is input order: cuisine iteration consumes seeded random samples in encounter order, and the database sorts only by distance. A probe with the same candidates and seed but reversed order changed the winner. Add stable ordering before sampling and tie-breaking, then test shuffled inputs. The stored snapshot also lacks the full candidate features and cuisine priors, while exclusion counts remain empty; store the permitted normalized inputs and policy/data versions needed to explain and replay a decision. Keep meal fit neutral until supported by actual meal evidence; the current lunch/dinner fit is identical. Version future ranking changes explicitly. ([Radius query](/Users/winstontang/Downloads/nosh/services/api/app/places/service.py:62), [Snapshot](/Users/winstontang/Downloads/nosh/services/api/app/suggestions/service.py:347))

The next release-blocking work is shared Supabase authentication with account-isolated state. Each current auth-hook invocation has its own local UUID token state; the global query cache uses keys such as `['contexts']` without a user ID, and sign-out does not cancel/clear queries. Code inspection identifies a stale cross-account display risk, not evidence of a deployed breach. Introduce one session owner, user-scoped queries and persisted state, and explicit cleanup on sign-out/deletion. Test switching accounts while requests are in flight. ([Auth hook](/Users/winstontang/Downloads/nosh/apps/mobile/src/hooks/useAuth.ts:22), [Context query](/Users/winstontang/Downloads/nosh/apps/mobile/app/(app)/index.tsx:40))

Complete offline card persistence and a durable action outbox, retaining one event ID and payload until acknowledgment. Existing proposal-response idempotency is a useful foundation. Context creation and proposal-free manual visits still need deduplication before automatic retries can be trusted; the global mutation policy currently retries once. Reconcile conflicts and require authentication recovery instead of blindly replaying every error. This API gap does not invalidate the newly hardened confirmation screen, which requires a proposal-backed visit. Add fault-injection tests for a server commit followed by a lost response, process restart and account switch. ([Retry policy](/Users/winstontang/Downloads/nosh/apps/mobile/app/_layout.tsx:5), [Context creation](/Users/winstontang/Downloads/nosh/services/api/app/contexts/service.py:14))

Finish location/radius/day controls and explicit context selection. The form still hardcodes the Mission anchor, and the home screen selects the first enabled context. Implement D017’s foreground use-time location with the saved anchor as fallback, without background access. Define how changing a context affects an existing session: Another currently reads current context settings while the session retains its creation version. Prefer an explicit immutable session context or a documented replacement-session rule, and decide how disabled contexts and location freshness affect eligibility. The API currently permits lookup/session creation for disabled contexts. Check real Apple Maps destinations, especially chain branches, instead of relying solely on name/address search. Complete EAS builds and real icons before external testers; keep Milestone 4 deferred. Add CI `alembic check` alongside the existing migration round-trip. Generated OpenAPI client types or a drift check would reduce future interface mistakes. Query tuning beyond the existing spatial index can wait for measured need. ([Context form](/Users/winstontang/Downloads/nosh/apps/mobile/app/(app)/contexts/new.tsx:36), [D017](/Users/winstontang/Downloads/nosh/DECISIONS.md:306), [Another context read](/Users/winstontang/Downloads/nosh/services/api/app/suggestions/service.py:286), [CI migration checks](/Users/winstontang/Downloads/nosh/.github/workflows/ci.yml:91))


## The checks pass; real-world readiness remains unproven

Fresh October 19 checks passed **249 tests: 12 root, 148 API unit, 46 PostgreSQL integration and 43 mobile tests**. Integration coverage includes six concurrent-database cases and migration downgrade/upgrade on disposable port 5433; the development database was not modified. Ruff lint/format, strict mypy, mobile TypeScript/ESLint, lock checks, `alembic check` and `git diff --check` passed. Online Expo dependency validation passed and Expo Doctor passed **18/18**. The mobile suite now includes seven confirmation-screen tests alongside 36 date-helper tests. ([Verification record](</Users/winstontang/Downloads/nosh/research_notes/Nosh restaurant data and architecture/repository.md>))

These runs used existing installed environments and the uncommitted hardening workspace; they were not a clean-machine install or a remote CI run. No live iOS build, device/offline test, provider coverage audit or production deployment was validated. This review changed no application code, dependencies or canonical product decisions. The next useful checkpoint is a small real catalog that survives refreshes and explains every recommendation, paired with reliable account and offline behavior. That will provide better evidence for the next investment than buying stars before establishing that the core discovery loop works.
